\section{Vehicle Knowledge Graph}
\label{sec:knowledge-graph}

\subsection{Why not just a PCAP archive}

A capture log answers "what bytes appeared on the wire." It does not answer "what does this vehicle do," "what depends on what," or "how confident are we." The Vehicle Knowledge Graph is the structured object that Section~\ref{sec:probe-discovery}'s discovery pipeline exists to build, and it is the only Option-B artifact that ever gets compiled into Machine IR.

\subsection{Graph-to-IR promotion policy}

\begin{decision}[title={Promotion threshold}]
A knowledge-graph edge is compiled into a Machine IR \code{Device}/\code{ResourceBinding} entry --- and therefore becomes callable through the Semantic API, even in a gated/monitor-only capacity --- only above a configured confidence threshold (default 0.90, tunable per safety class of the target function; higher for anything that will ever be actuated, lower acceptable for read-only telemetry). Below threshold, the mapping is visible in graph-browsing/debug tooling but not exposed as an API-callable Device. This keeps "Alfred thinks it found something" and "Alfred will let you use it" architecturally distinct, which is the same discipline Section~\ref{sec:active-control} applies at the command level.
\end{decision}

Every edge in the graph --- not just terminal signal mappings --- carries its own confidence and evidence references, because dependencies compound: a signal mapping inferred from an experiment run while the vehicle was in an unusual state (e.g., ignition off) should not silently inherit high confidence if the \emph{network path} through which it was observed is itself uncertain (e.g., ambiguous gateway routing). The graph stores confidence per edge specifically so the promotion policy can require the \emph{weakest} link in a path to clear the threshold, not just the leaf signal.
